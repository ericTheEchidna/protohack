## Phase N2 — Tile Support

Wire NetHack's tile infrastructure into the Meson build so that tile data
is compiled in and accessible to windowports by default. Prerequisite:
Phase N1 (Meson build) complete and producing a working TTY binary.

The tile infrastructure already exists in the source tree. This task
makes it build, not invent it.

### Context

NetHack's tile system lives in `win/share/`:
- `tileset.c` / `tileset.h` — tileset loading and management
- `tile.c` — tile data and glyph-to-tile mapping
- `tilemap.c` — generated at build time; maps NetHack objects to tile indices
- `tile2bmp.c` — BMP tileset converter (build-time utility, not runtime)
- `tiletxt.c`, `tiletext.c` — text-format tile data

`tilemap.c` is generated by the `util/tilemap` build-time tool (similar
to `makedefs`). It must be produced as a custom Meson target before
compilation.

The reference tileset for testing is `nhtiles.bmp` (referenced in the
linux.370 hints as `VARDATND0`). It ships with NetHack source in `dat/`.

The hack2bridge windowport (future task) will use tile indices from this
system directly — it emits a `tile` field per cell from the same index
table. Getting this right here means the windowport just calls the
existing lookup, not a parallel one.

### Tasks

- [ ] Audit `win/share/tile.c`, `tileset.c`, `tilemap.c` — understand
      the public API (likely `glyph2tile[]` array and `read_tiles()` or
      similar)
- [ ] Add `util/tilemap` as a Meson custom target:
  - [ ] Compile `util/tilemap.c` → `tilemap` executable
  - [ ] Run `tilemap` → `win/share/tilemap.c` (generated source)
  - [ ] Add generated `tilemap.c` to the tile source list
- [ ] Add tile sources to `meson.build`:
  - [ ] `win/share/tile.c`
  - [ ] `win/share/tileset.c`
  - [ ] Generated `win/share/tilemap.c`
  - [ ] `win/share/tiletext.c` (if needed at runtime)
  - [ ] Add `TILES` or equivalent define so NetHack core knows tiles
        are available
- [ ] Verify the tile data file (`dat/nhtiles.bmp`) is installed to the
      expected data directory at build time (Meson `install_data`)
- [ ] Confirm `glyph2tile[]` is accessible from a windowport — this is
      the array the hack2bridge windowport will query per cell
- [ ] TTY binary still works after adding tile sources (tiles are
      compiled in but TTY ignores them — regression check)

### Source references

- `win/share/tile.c`, `tileset.c`, `tilemap.c` — runtime tile code
- `win/share/tileset.h`, `tile.h` — headers; check what a windowport needs
- `util/tilemap.c` — tile index generator (build-time utility)
- `sys/unix/hints/linux.370` — `VARDATND0` lines show which tile data
  files are expected
- `include/tileset.h` — top-level tileset header

### Complexity notes

- `tilemap.c` is generated, not checked in. If it appears to exist in the
  repo, verify it is not stale from an old build. Regenerate via the
  custom target, do not use a cached copy.
- The `glyph2tile[]` array size is determined at build time from the
  number of NetHack glyphs. It will change as 3.7 adds monsters/items.
  Do not hardcode its size anywhere.
- Tile support does not require a graphical windowport to compile in —
  the array and loader are windowport-agnostic. Resist the temptation to
  guard them behind `#ifdef USE_TILES` unless the existing code already
  does so.
- Do not add Qt or X11 dependencies in this task. Tile data and the index
  table are the goal; rendering is the windowport's job.

### Done when

- `meson setup builddir && ninja -C builddir` still completes cleanly
- `glyph2tile[]` is populated at runtime and queryable from a windowport
- `nhtiles.bmp` (or equivalent tile data) is installed alongside the binary
- TTY windowport still functions (no regression)
- The tile index for the player glyph (`@`) returns a non-zero value
  (quick sanity check confirming the table is populated)
